# Zombie 프로젝트 스크립트 작업 하네스

현재 확장 작업의 범위와 완료 기준은 `NEXT_WORK_CHECKLIST.md`를 함께 참고한다.

이 파일은 이 `Assets` 폴더와 하위 경로에서 Unity C# 스크립트를 작성하거나 수정할 때 적용한다.

## 1. 프로젝트 기준

- 엔진: Unity `6000.3.10f1`
- 렌더 파이프라인: URP `17.3.0`
- 게임 형태: PC 키보드·마우스 기반 싱글플레이 TPS 프로토타입
- 기획 기준 문서: 이 폴더의 `TPS_좀비_서바이벌_상세기획서_v0.1.md`
- 주 스크립트 경로: `Assets/Scripts`
- 외부 에셋과 패키지 파일은 요청 범위에 포함될 때만 수정한다.

기획서의 표와 규칙은 구현 근거로 사용하되, 문서에서 `제안`, `검증용`, `미정`, `보류`로 표시한 내용은 확정 사양으로 취급하지 않는다. 구현에 필요한 선택이 기존 코드나 사용자 요청으로 결정되지 않으면 임의로 제품 범위를 넓히지 말고, 최소한의 프로토타입 가정을 코드와 작업 결과에 명시한다.

이 파일은 작업 절차와 구현 경계를, 기획서는 게임 설계를, `NEXT_WORK_CHECKLIST.md`는 작업 범위와 진행 증거를 관리한다. 충돌 시 최신 사용자 요청을 우선하고 현재 코드·씬·프리팹의 실제 동작과 설계 목표의 차이를 기록한다. 문서에 적힌 목표는 그 자체로 구현 승인이나 완료 증거가 아니다.

## 2. 작업 원칙

1. 요청과 직접 관련된 기존 코드를 먼저 읽고 호출 관계, Inspector 참조, 프리팹 의존성을 확인한다.
2. 기존 동작을 유지하면서 필요한 범위만 변경한다. 관련 없는 이름 변경, 폴더 이동, 전면 재작성은 하지 않는다.
3. 한 스크립트에 세션, 웨이브, AI, 보급, UI 책임을 모으지 않는다.
4. 정의 데이터와 런타임 상태를 분리한다. 반복 조정할 수치는 `ScriptableObject` 또는 직렬화된 설정으로 둔다.
5. UI는 상태를 읽고 표시한다. 적 생성, 자원 소모, 승패 판정 같은 게임 규칙을 UI에서 직접 실행하지 않는다.
6. 기능 완료 후 컴파일 오류, 주요 상태 전환, 요청과 관련된 예외 상황을 확인한다.

### 2.1 UI·오브젝트·프리팹은 Unity 에디터에서 구성하고 연결

- UI의 Canvas, TMPro 텍스트, 이미지, 버튼, 레이아웃과 씬 오브젝트·컴포넌트·프리팹 구성은 Unity 에디터에서 직접 작성하고 연결한다. 코드로 UI 계층이나 씬 구성을 자동 생성하는 방식으로 구현하지 않는다.
- UI·다른 씬 오브젝트·프리팹·데이터 에셋 참조는 `[SerializeField] private` 필드로 노출하고 Inspector에서 지정한다. 코드에서는 연결된 참조의 상태·표시·게임 동작을 갱신한다.
- 연결 누락을 숨기려고 `new GameObject`, `AddComponent`, `Find`·태그 검색 또는 고정 `Resources.Load` 경로로 필요한 구성이나 참조를 자동으로 만들어 채우지 않는다. 동일 오브젝트의 이미 부착된 컴포넌트를 `GetComponent`로 확인·캐시하는 것은 허용한다.
- 에디터에서 해야 할 연결을 대신하기 위한 자동 배치·프리팹 생성·참조 연결용 Editor 스크립트나 씬·프리팹 YAML 직접 편집은 사용자가 명시적으로 요청한 경우에만 수행한다.
- 좀비·아이템·투사체·효과처럼 게임 규칙에 필요한 런타임 스폰은 Inspector에 연결된 프리팹을 `Instantiate`하거나 미리 구성한 풀에서 꺼내 사용한다. 스폰 로직은 허용하되 프리팹의 컴포넌트·자식 구조와 필수 참조는 에디터에서 완성한다.
- 작업 결과에 에디터 설정 절차를 함께 제공한다: 생성할 오브젝트와 계층, 부착할 컴포넌트, Inspector 필드별 연결 대상, 프리팹·데이터·Layer·Tag 설정, 확인할 동작. 코드 작성 완료와 에디터 연결·Play Mode 검증 완료를 구분한다.
- 기존 코드에 자동 생성·연결 방식이 있더라도 관련 없는 부분을 일괄 재작성하지 않는다. 새로 구현하거나 이번 요청으로 수정하는 기능에 이 규칙을 적용한다.

### 2.2 작업 시작과 기능별 진행 순서

1. `git status --short`로 기존 변경을 확인한다. 다른 작업에서 생긴 변경을 덮어쓰거나 일괄 정리하지 않는다.
2. 요청과 관련된 코드·씬·프리팹·데이터의 실제 연결을 확인한다. HUD는 `SurvivalHud`·`UIManager`, 플레이어와 무기는 `PlayerHealth`·`PlayerShooter`·`Gun`·`GunData`, 웨이브와 적은 `ZombieSpawner`·`EnemyRegistry`·`Zombie`, 보급은 `ItemSpawner`·`RandomWeaponSpawner`를 시작점으로 호출 관계를 추적한다. 경로와 클래스 이름은 현재 저장소에서 확인한다.
3. 한 번에 한 플레이 가능한 기능 묶음을 마무리한다. 데이터 정의 → 런타임 상태·규칙 → 에디터 구성·Inspector 연결 → HUD·알림 → 정상·경계 조건 검증 순서로 진행한다.
4. 코드 작성, 에디터 연결, Play Mode 검증을 별도로 기록한다. 체크리스트의 통합 완료 표시는 세 단계의 증거가 모두 있을 때만 갱신한다. 실행 검증이 불가능하면 미검증 사실과 수동 확인 절차를 남긴다.

과거의 스크린샷이나 작업 기록은 해당 시점·조건의 증거다. 이전 문서의 미구현 목록이나 진행 중 단계는 현재 상태로 복사하지 않고 코드를 다시 확인한다. 한 해상도의 HUD 확인으로 다른 해상도의 정상 표시까지 완료로 취급하지 않는다.

## 3. 책임 경계

다음 책임을 기준으로 클래스를 분리한다.

- `Session`: 준비, 전투, 승리, 패배 전환과 승패 우선순위
- `WaveDirector`: 웨이브별 예정 생성 큐, 생성 지연, 웨이브 완료 판정
- `EnemyRegistry`: 살아 있는 적 수, 소환 귀속 수, 전체 생성 슬롯의 예약과 반환
- `Enemy AI`: 이동, 목표 선택, 공격, 소환 상태 전환
- `ResourceSpawner`: 생성 주기, 가중치 추첨, 배치 지점과 필드 상한
- `Inventory` / `Interaction`: 보유량, 작업 예약, 취소, 완료 시 소모
- `HUD`: 현재 상태 표시와 사용자 피드백

클래스 간 통지는 명확한 메서드 또는 이벤트로 처리한다. 전역 싱글턴을 새로 추가하기 전에 기존 소유자나 직렬화 참조로 연결할 수 있는지 검토한다. 같은 적의 생성·사망 이벤트가 중복 등록되거나 개체 수가 두 번 차감되지 않게 한다.

## 4. 데이터 작성 규칙

조정 가능한 게임 정의는 다음 단위로 분리하는 것을 우선한다.

- `EnemyDefinition`: ID, 최대 HP, 이동 속도, 피해, 공격 간격, 선택적 소환 설정
- `SummonProfile`: 생성 수, 예고 시간, 재사용 대기시간, 횟수·생존 상한, 최소·최대 반경
- `WaveDefinition`: 웨이브 ID, 일반 적 수, 생성 구간, 특수 적 등장 시점, 허용 방향
- `ItemDefinition`: ID, 정수 가중치, 획득량, 소지 한도
- `BarricadeLevel`: 단계, 최대 내구도, 비용, 작업 시간
- `SpawnPoint`: ID, 위치, 구역, 활성 상태

런타임 HP, 현재 상태, 인스턴스 ID, 소환자 소유 관계, 남은 타이머를 정의 에셋에 기록하지 않는다. `ScriptableObject`는 공유 설정으로만 사용하고 플레이 도중 원본 에셋 값을 변경하지 않는다.

초기화 시 다음을 검증하고 잘못된 설정에는 오브젝트 문맥을 포함한 명확한 오류를 남긴다.

- 필수 프리팹과 참조가 `null`이 아닌가
- 배열과 목록에 사용할 항목이 하나 이상 있는가
- ID가 비어 있거나 중복되지 않았는가
- 시간, 수량, HP, 가중치가 허용 범위인가
- 최소 반경이 최대 반경보다 크지 않은가
- 참조 ID와 생성 지점이 실제로 존재하는가
- 확률표가 기획에서 요구한 합계를 만족하는가

가중치 선택은 정수 누적 가중치로 구현한다. 배열 자체를 `Instantiate`에 전달하지 말고 먼저 유효한 단일 프리팹을 선택한다. 빈 배열에서 `Random.Range`를 호출하지 않는다.

## 5. C# 및 Unity 작성 규칙

- 클래스와 공개 멤버는 `PascalCase`, 지역 변수와 매개변수는 `camelCase`를 사용한다.
- Inspector 노출은 가능한 한 `[SerializeField] private`을 사용한다. 다른 클래스가 변경할 이유가 없는 필드는 `public`으로 열지 않는다.
- 숫자와 문자열을 로직에 반복해서 직접 쓰지 않는다. 조정값은 직렬화 필드, 데이터 에셋 또는 이름 있는 상수로 둔다.
- 컴포넌트 참조는 `Awake` 또는 명시적 초기화 단계에서 확보한다. 매 프레임 `Find`, `GetComponent`, 태그 검색을 반복하지 않는다.
- `Update`에서는 입력과 프레임 단위 갱신만 수행한다. 비싼 탐색과 경로 재계산은 간격을 제한한다.
- 물리 이동은 `FixedUpdate`, 입력과 카메라는 `Update`/`LateUpdate`의 역할을 지킨다.
- 코루틴과 지연 콜백은 비활성화, 사망, 재시작 시 중단하거나 무효화한다.
- 이벤트는 구독한 주체가 적절한 생명주기에 해제한다. 람다를 사용해 해제가 불가능해지는 구조를 피한다.
- 오브젝트 파괴 뒤 실행될 콜백과 중복 사망 처리를 방지한다.
- 게임 시간에 종속된 타이머는 일시정지 시 함께 멈춰야 한다. 일시정지를 무시해야 하는 UI만 unscaled time을 사용한다.
- 사용자에게 의미 없는 주석은 추가하지 않는다. 주석은 코드가 무엇을 하는지보다 규칙의 이유, 우선순위, 예외를 설명한다.
- 파일 이름과 주 `MonoBehaviour`/`ScriptableObject` 클래스 이름을 일치시킨다.

## 6. 상태와 수치 규칙

- 세션 상태는 준비, 전투, 승리, 패배를 명시적으로 표현한다.
- 적 AI와 소환 행동은 불리언 조합보다 enum 기반 상태를 우선한다.
- 상태 전환 시 진입 조건, 종료 조건, 취소 처리, 예약 자원 반환을 한곳에서 확인할 수 있게 한다.
- 같은 프레임에 최종 적 처치와 플레이어 또는 보관소 파괴가 겹치면 패배를 우선한다.
- 웨이브 완료는 예정 생성 큐가 비고, 모든 예정 생성이 끝났으며, 살아 있는 적이 0일 때만 성립한다.
- 피해와 회복 계산은 최종 단계에서 정수화하고 HP와 수량은 `0..최댓값`으로 제한한다.
- 재장전, 회복, 수리, 강화는 완료 시점에 탄약·아이템·판자를 이동하거나 소모한다. 취소 시 중복 소모가 없어야 한다.
- 생성 상한은 검사와 실제 생성 사이의 경쟁을 막기 위해 슬롯을 먼저 예약하고, 실패·취소·사망 시 반드시 반환한다.
- 밀린 생성은 한 프레임에 몰아서 처리하지 않는다.
- 재현이 필요한 웨이브와 보급 테스트는 시드를 외부에서 주입할 수 있게 설계한다.

## 7. 전투와 AI 불변 조건

- 카메라 조준점과 총구 사이 장애물을 다시 검사해 벽 관통 사격을 막는다.
- 근접 타격 순간 거리와 차단물을 다시 검사한다.
- 목표 재선택과 경로 재계산에는 최소 간격을 둔다.
- 소환 예고 중 소환자가 사망하면 소환, 예약 슬롯, 예고 표시를 모두 취소한다.
- 소환에 성공한 일반 좀비는 소환자가 죽어도 유지한다.
- 소환 위치는 이동 가능한 바닥, 충돌 없음, 실내 아님, 플레이어 안전거리, 거점 경로를 확인한다.
- 유효한 소환 위치가 일부만 있으면 가능한 수만 생성한다. 전부 실패하면 횟수를 소모하지 않고 재시도한다.
- 전체 적 상한과 소환자별 귀속 상한을 동시에 지킨다.

## 8. 오류 처리와 Inspector 안전성

- 필수 설정 누락을 조용히 무시하지 않는다. 실행 불가능한 기능은 안전하게 중단하고 원인을 구체적으로 로그에 남긴다.
- 선택 기능은 속성이나 참조가 없을 수 있음을 전제로 한다. Editor 확장에서 선택적 `MaterialProperty`는 필수 검색으로 가져오지 않는다.
- `OnValidate`는 설정 검증과 값 제한에 사용하되, 씬 오브젝트를 대량 생성하거나 런타임 상태를 변경하지 않는다.
- Editor 전용 코드는 `Editor` 폴더 또는 Editor 전용 어셈블리에 둔다.
- 서드파티 에셋 오류를 수정해야 한다면 원본을 직접 수정할 필요와 업데이트 시 덮어쓰기 위험을 작업 결과에 기록한다.

## 9. 검증 기준

변경 범위에 맞춰 다음 순서로 검증한다.

1. Unity/C# 컴파일 오류가 없는지 확인한다.
2. Inspector의 필수 참조와 데이터 검증 메시지를 확인한다.
3. 정상 흐름을 한 번 실행한다.
4. 수정한 규칙과 직접 관련된 경계 조건을 실행한다.
5. 재시작 후 이전 타이머, 이벤트, 예약, 적 등록 정보가 남지 않는지 확인한다.

관련 기능을 수정할 때 우선 확인할 대표 시나리오는 다음과 같다.

- 소환 예고 마지막 순간 소환자 사망
- 두 소환자의 동시 생성과 전체/귀속 상한
- 소환 위치 일부 또는 전체 차단
- 예정 생성 대기열이 남은 상태에서 적 수가 0이 됨
- 수리 중 바리케이드 파괴
- 소지 한도 직전 보급 획득과 필드 잔량
- 일시정지 후 모든 게임 타이머 재개
- 최종 처치와 패배 조건의 동시 발생
- 세션 재시작 후 중복 콜백 없음

테스트는 구현을 그대로 복제하는 형식보다 상태 전환, 상한, 취소, 우선순위 같은 실패 위험이 큰 규칙을 검증한다. 성능 최적화는 전체 적 30마리, 필드 보급 12개, 동시 소환 예고 조건에서 측정한 병목을 근거로 수행한다.

## 10. 작업 결과 보고

스크립트 작업을 마치면 다음을 간단히 보고한다.

- 변경한 파일과 동작
- 선택한 구조와 그 이유
- 적용한 기획 규칙 및 가정
- 수행한 검증과 결과
- Unity Editor에서 사용자가 연결해야 하는 프리팹, 데이터 에셋, Layer, Tag 또는 Inspector 필드
- 확인하지 못한 항목과 남은 위험

기획서와 구현이 충돌하면 현재 코드의 실제 동작을 숨기지 말고 차이를 명시한다. 확정되지 않은 수치를 임의로 확정했다고 표현하지 않는다.

## 11. 무기·HUD·보급 구현 범위와 추가 경계

아래는 2026-09-23 설계에서 이어받은 기능 목표와 구현 경계다. 현재 구현 완료 목록이나 일괄 구현 지시가 아니며, 최신 사용자 요청·기획서·체크리스트에서 변경된 규칙을 우선한다. 특히 바리케이드는 최신 자동 설치·아이템 강화 설계를 따른다.

| 영역 | 이어받은 목표 |
|---|---|
| HUD | 좌하단 나침반형 표시로 시선 방향과 주변 적의 대략적 위치 표시. 하단 중앙 체력바·수치. 우하단 탄약·주/보조 무기 종류·수류탄 수. 무기 생성·웨이브 알림. |
| 주무기 | AR 기본형, 스나이퍼 관통 공격(통상 1~2명, 조건부 최대 3명이라는 초기 구상), 근거리 고화력 샷건. 관통 조건과 수치는 최신 설계 확인 후 적용. |
| 보조무기 | 낮은 피해의 무한 탄약 권총과 높은 피해의 근접무기. 근접무기 3종은 구상 단계이며 채택 여부를 확인. |
| 투척·보급 | 수류탄 범위 피해. 체력 회복·탄약·속도 증가·수류탄 보충의 무작위 보급. 생성 확률·위치는 최신 파밍·거점 설계 확인 후 적용. |
| 무기 아이템 | AR·스나이퍼·샷건·권총·근접무기의 무작위 생성. 교체한 이전 무기는 보관하지 않고 다시 생성되면 재획득 가능하다는 초기 설계. 변경 여부를 확인. |
| 피격·방어 | 헤드샷 추가 피해. 거점 바리케이드 강화와 단계별 내구도·작업 시간. 최신 급소·도전 과제·자동 설치 설계와 함께 확인. |

- 무기 정의(종류·피해·탄약·사거리·관통·산탄 설정)와 런타임 상태(장탄수·예비탄·장착 슬롯)를 분리한다. HUD는 상태를 읽고 발사나 아이템 소비 규칙을 소유하지 않는다.
- 피격은 `RaycastHit`의 실제 타격 부위를 식별해 피해 계산으로 전달한다. 관통은 같은 발사에서 동일 대상에 중복 피해를 주지 않으며 장애물·아군·최대 대상 수 규칙을 명시한다. 산탄과 급소 집계의 중복 처리도 별도로 정의한다.
- 무기 아이템과 보급품 생성의 소유자를 명확히 하고 기존 생성기와 중복 지급하지 않는다. 유효한 NavMesh·지면 위치를 찾지 못하면 안전하게 생성을 건너뛰고 실패를 관찰 가능하게 한다.
- 나침반 적 표시는 등록된 살아 있는 적만 대상으로 한다. 거리 제한·좌표 변환·카메라 회전을 구분하고, 스폰 좌표나 AABB 문제의 해결 여부를 실제로 확인한다.
- 무기 슬롯을 수정할 때 초기 주/보조 프리팹, `Gun`, `GunData`, `Fire Transform`, `Left Handle`, `Right Handle` 연결과 기존 씬 무기의 중복 표시를 확인한다. `PlayerShooter.EquipWeapon` 등 실제 API를 먼저 읽고 슬롯 교체·재획득·탄약 유지·HUD 갱신을 검증한다. 보조 슬롯이 비어 있을 때의 전환 동작도 확인한다.
- 바리케이드 단계·내구도·강화 비용·작업 시간은 설정 데이터로 관리한다. 작업 중단·사망·파괴·웨이브 전환 시 처리와 실제 웨이브 완료 조건의 연동을 명시한다.

기능별 작업은 기반·HUD, 무기 획득·교체, 개별 전투 방식, 보급·웨이브, 거점 방어 단위로 나눌 수 있다. 실제 우선순위는 최신 체크리스트와 기능 의존관계에 따른다.

관통 확률·조건, 산탄 수·퍼짐·유효 거리, 무한 탄약과 재장전의 관계, 근접무기 채택, 수류탄 한도·반경·피해, 속도 효과 배율·지속 시간, 헤드샷 배율, 아이템 주기·확률·상한, 바리케이드 조건·단계별 수치, 알림 시간·우선순위는 기존 코드와 최신 설계에서 결정 여부를 확인한다. 이미 결정된 항목은 다시 미정으로 돌리지 않는다. 남은 미정 항목은 조정 가능한 최소 가정을 기록하고 게임 규칙을 바꾸는 결정은 사용자에게 확인한다.
